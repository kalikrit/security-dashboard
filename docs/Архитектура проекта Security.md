# Архитектура проекта "Security Analytics Dashboard"

**Дата фиксации:** 2025-05-15  
**Контекст:** Проект для портфолио и собеседования в компанию ТТК (требования: Django/Django-Ninja, Svelte/SvelteKit, TypeScript, дашборды/графики/таблицы).

## 1. Цель проекта
Разработать дашборд аналитики информационной безопасности, отображающий:
- Временной ряд инцидентов
- Топ типов угроз
- Распределение по критичности (High/Medium/Low)
- Таблицу инцидентов с пагинацией и фильтрацией
- (Опционально) график уязвимостей (CVSS)

## 2. Принятые архитектурные решения

### 2.1. Бэкенд: Django + Django-Ninja
- **Роль:** REST API, бизнес-логика, генерация тестовых данных, хранение в PostgreSQL.
- **Отказ от Celery/Redis:** Для упрощения деплоя на бесплатных площадках и соответствия MVP. Данные обновляются при запросе (при открытии дашборда или по нажатию кнопки Refresh).
- **Генерация данных:** Встроенный в Django генератор случайных инцидентов (модель `SecurityIncident`). При старте сервера можно заполнить БД тестовыми записями (1000+ событий).
- **Эндпоинты (Django-Ninja):**
  - `GET /api/incidents/summary` – сводка
  - `GET /api/incidents/timeline?days=7` – временной ряд
  - `GET /api/incidents/top-types?limit=5` – топ угроз
  - `GET /api/incidents/list?page=1&limit=20` – таблица с пагинацией
  - (дополнительно) `POST /api/incidents/generate` – ручная генерация новых данных

### 2.2. Фронтенд: SvelteKit (TypeScript)
- **Роль:** UI дашборда, графики (Chart.js), таблицы, фильтры.
- **Использование SSR:** Load-функции для получения начальных данных при первом рендере страницы. После гидратации клиент может обновлять данные асинхронно (без перезагрузки).
- **Компоненты:**
  - MetricCard (карточки с числами)
  - LineChart (график временного ряда)
  - BarChart (гистограмма типов угроз)
  - IncidentTable (таблица с сортировкой/фильтром)
  - SeverityBadge (цветовой индикатор)
- **Стейт-менеджмент:** Svelte stores (`writable`/`derived`) для управления фильтрами и состоянием загрузки.

### 2.3. Взаимодействие фронта и бэка
- SvelteKit (порт 3000) обращается к Django API (порт 8000) через `fetch` в `load` функциях (на сервере) и в клиентских обработчиках (например, кнопка Refresh).
- Адрес API задаётся через переменные окружения (`VITE_API_BASE_URL` в SvelteKit).

### 2.4. База данных
- **PostgreSQL** (управляемая через Render.com). Модель `SecurityIncident`:
  - `timestamp` (DateTimeField)
  - `incident_type` (choices)
  - `severity` (choices)
  - `source_country` (CharField)
  - `cve_id` (CharField, опционально)
  - `status` (choices: Open, InProgress, Closed)
- Для MVP можно использовать SQLite локально, в production – PostgreSQL.

## 3. Деплой (бесплатные площадки, без оплаты)

| Компонент | Платформа | Бесплатные условия |
|-----------|-----------|---------------------|
| Django + PostgreSQL | [Render.com](https://render.com) | Web Service (750 часов/мес) + бесплатный PostgreSQL (512 MB RAM) |
| SvelteKit | [Vercel.com](https://vercel.com) | Бесплатный тариф (автодеплой из Git, SSL) |

**Альтернатива при невозможности зарегистрироваться на Render:** использовать SQLite и развернуть Django на PythonAnywhere (но без PostgreSQL) или использовать Railway.app (тоже есть бесплатный тариф).

## 4. Отказ от Celery и внешних API
- **Причина:** Бесплатные платформы не позволяют запускать несколько сервисов (Django + Celery worker + Redis) без оплаты.
- **Решение:** Данные генерируются внутри Django при старте или по специальному эндпоинту. Обновление по кнопке "Refresh" на фронте.
- **На собеседовании:** Объяснить, что в production-версии с реальными данными (например, SIEM-система) потребуется Celery + брокер для фонового опроса внешних API, но в демо-проекте мы упростили архитектуру для бесплатного хостинга.
